# Retail Customer RFM Analytics

## Project Overview

This project analyzes customer transaction behavior for **GulfMart Retail**, a fictional Saudi/GCC omnichannel retailer.

The objective is to use customer transaction data to understand customer value, purchasing behavior, engagement, and retention risk.

The project combines:

* Python
* Pandas
* NumPy
* SQL Server
* Power BI
* RFM Analysis
* Customer Segmentation
* Customer Value Analysis
* Retention Analysis

The final objective is to translate customer analytics into actionable CRM, loyalty, retention, and growth strategies.

---

## Business Problem

GulfMart has extensive customer transaction data but lacks a systematic framework for understanding customer value, purchasing behavior, engagement, and retention risk.

Management needs to identify:

* Valuable customers
* Loyal customers
* High-frequency customers
* At-risk customers
* Inactive customers
* Reactivation opportunities
* Customer growth opportunities

The analysis will convert transaction-level data into customer-level insights and business actions.

## Synthetic Data Generation

Because a suitable dataset was not available for the specific business requirements of this project, the project uses a **controlled synthetic data-generation framework** rather than an arbitrary public dataset.

The generator is designed to create realistic retail behavior while maintaining reproducibility through a fixed random seed and centralized configuration.

### Generation Architecture

```text
Generation Configuration
          ↓
Configuration Validation
          ↓
Customer / Product / Store / Date Dimensions
          ↓
Customer Behavior Profiles
          ↓
Customer Category Affinity
          ↓
Seasonality
          ↓
Final Category Probabilities
          ↓
Transaction / Basket Generation
          ↓
Pricing / Discounts / Cost / Profit
          ↓
Returns & Data-Quality Issues
          ↓
Raw Dataset
```

### Customer Behavior Profiles

The generator uses hidden behavioral profiles to create realistic differences between customers.

Current profiles include:

* High Engagement
* Regular
* Occasional
* Low Engagement
* Lapsed-Prone

These profiles are **generation mechanisms**, not final analytical customer segments.

The final RFM segments will be calculated independently from the generated transaction data.

### Customer Category Affinity

Customers receive individual category preferences rather than using exactly the same category distribution for every customer.

Customer category affinity is generated from the overall GulfMart category mix with controlled customer-level variation.

This allows different customers to naturally develop different purchasing preferences.

For example, one customer may have a stronger affinity for:

* Grocery
* Dairy
* Fresh Food

while another customer may have relatively stronger affinity for:

* Beverages
* Snacks
* Personal Care

The category-affinity layer is used to generate transaction behavior and is not treated as an analytical customer segment.

### Seasonality

The transaction generator incorporates seasonal retail demand patterns for:

* Ramadan
* Eid
* Summer
* Back-to-School

The project uses fixed synthetic analytical windows to keep the dataset reproducible.

Seasonality affects category-selection probabilities rather than forcing deterministic purchases.

For example, during a summer period, beverages and frozen food may receive higher category-selection weights, while other categories may remain unchanged or receive smaller adjustments.

### Final Category Probability Methodology

Customer preferences and seasonality are combined using:

```text
Customer Category Affinity
          ×
Seasonality Multiplier
          ↓
Adjusted Category Weight
          ↓
Normalization
          ↓
Final Category Probability
```

The calculation is:

**Adjusted Category Weight = Customer Category Affinity × Seasonality Multiplier**

The adjusted weights are then normalized:

**Final Category Probability = Adjusted Category Weight / Total Adjusted Weight**

This approach allows both persistent customer preferences and time-dependent retail behavior to influence transaction generation.

### Generation QA

The category-probability generation layer has been validated to confirm:

* Category probabilities sum to approximately 1.0.
* No negative probabilities are generated.
* All configured categories are represented.
* Seasonal periods affect category probabilities.
* Different customers can have different category probabilities.
* Normal periods use a neutral multiplier of 1.0.

The current generation framework has successfully passed these checks before transaction generation.

### Important Modeling Principle

The generator creates underlying behavior that will later be **discovered through analysis**.

For example, a Ramadan multiplier is a data-generation assumption. It must not later be reported as an observed business result unless the generated transaction data actually demonstrates that pattern.

Similarly:

**Revenue ≠ Profitability**

The generator therefore retains sales, cost, and gross-profit information so customer value can later be evaluated from both revenue and profitability perspectives.

## Data Architecture

The analytical model will use a retail star-schema structure:

```text
                 dim_customer
                      |
                      |
dim_product ---- fact_sales ---- dim_store
                      |
                      |
                   dim_date
```

### Fact Table

`fact_sales`

Expected grain:

> One product line within a transaction.

Potential fields:

* `sales_line_id`
* `transaction_id`
* `transaction_date`
* `customer_id`
* `product_id`
* `store_id`
* `quantity`
* `unit_price`
* `discount_amount`
* `net_sales`
* `cost`
* `gross_profit`
* `channel`
* `transaction_type`

A single transaction can contain multiple product lines.

Therefore:

> Fact rows are not the same as transactions.

RFM Frequency will use **distinct qualifying transaction IDs**, rather than simply counting fact rows.

### Dimension Tables

#### `dim_customer`

Customer-level attributes.

Expected fields include:

* `customer_id`
* `customer_name`
* `gender`
* `age_group`
* `city`
* `region`
* `customer_join_date`
* `customer_type`

#### `dim_product`

Product and category attributes.

Expected fields include:

* `product_id`
* `product_name`
* `category`
* `subcategory`
* `brand`
* `unit_cost`
* `unit_price`

#### `dim_store`

Store and geographic attributes.

The model includes physical stores and an e-commerce pseudo-store.

#### `dim_date`

Calendar attributes used for time-based analysis.

## RFM Analysis

Customer behavior will be analyzed using:

### Recency

How recently did the customer purchase?

Lower recency days generally indicate more recent engagement.

### Frequency

How frequently did the customer purchase?

Frequency will be based on qualifying distinct transactions rather than simply counting transaction lines.

### Monetary

How much value did the customer generate?

Monetary value will initially be based on qualifying customer sales and will be validated against the business transaction rules.

### Analysis Date

The initial RFM reference date will be:

```text
Maximum valid transaction date + 1 day
```

This creates a reproducible analysis snapshot based on the dataset rather than using today's date.

---

## RFM Scoring

Customers will initially receive scores from 1 to 5:

* Recency: 1 = least recent, 5 = most recent
* Frequency: 1 = lowest, 5 = highest
* Monetary: 1 = lowest, 5 = highest

Quantile-based scoring will be evaluated after inspecting the actual distributions and ties in the data.
